# Vendor Request Workflow Contract

## Contract metadata

- Contract owner: `@sillypoise`.
- Product owner: `@sillypoise`.
- Version: `v1-draft`.
- Compatibility status: Pre-release; no external consumers exist.
- Boundary: Authenticated application operations that read or mutate vendor requests.

This document is normative unless a section is explicitly labeled as an example.

## Trust and authority

Authentication identifies a user. Active organization membership and role records authorize each
operation. Request identifiers, organization identifiers, owner identifiers, roles, and reviewer
identifiers supplied by a client are never accepted as authority.

All reads and writes are scoped to the authenticated user's active organization. A failed or absent
policy decision denies the operation. Version 1 permits one organization membership per user; an
inactive membership grants no access. Membership display names are presentation data and never an
authority claim.

## Required request fields

A request must persist these fields before submission:

| Field | Requirement |
| --- | --- |
| `vendor_legal_name` | Trimmed text from 1 through 160 characters. |
| `vendor_website` | Absolute HTTPS URL with a maximum of 2,048 characters. |
| `service_category` | `software`, `professional_services`, `facilities`, `logistics`, or `other`. |
| `business_justification` | Trimmed text from 20 through 2,000 characters. |
| `annual_spend_minor_units` | Integer from 0 through 1,000,000,000 inclusive. |
| `currency_code` | `USD` in version 1. |
| `receives_confidential_data` | Boolean. |
| `supports_critical_process` | Boolean. |

Drafts may be incomplete. Submission validates the complete required field set before any workflow
state or audit event is changed.

The authenticated database context supplies request ownership and organization scope. The client
cannot choose these fields during creation.

## Draft operations

`create_vendor_request` accepts a `vendor_request_draft_input` containing all eight request fields.
Each field may be explicitly null while the request is a draft. It returns the created request with
database-derived identity, organization, state, revision, and timestamps. Creation starts at
revision 1 and records one `created` audit event.

`update_vendor_request` accepts a request identifier, expected revision, and a
`vendor_request_draft_input` that completely replaces all eight request fields. Only the request
owner may call it in `draft` or `changes_requested`. It returns the updated request and increments
the revision exactly once. Draft field edits do not create audit events because the audit timeline
records lifecycle actions rather than field history.

## States

- `draft`
- `submitted`
- `in_review`
- `changes_requested`
- `approved`
- `rejected`

`approved` and `rejected` are terminal in version 1.

## Allowed transitions

- `draft` → Submit → `submitted`.
  - Actor: Request owner.
  - Preconditions: All required fields are valid.
- `submitted` → Assign → `in_review`.
  - Actor: Organization administrator.
  - Preconditions: The reviewer is active and belongs to the request organization.
- `in_review` → Approve → `approved`.
  - Actor: Assigned reviewer.
  - Preconditions: The request has not changed since review began.
- `in_review` → Reject → `rejected`.
  - Actor: Assigned reviewer.
  - Preconditions: A decision reason is present.
- `in_review` → Request changes → `changes_requested`.
  - Actor: Assigned reviewer.
  - Preconditions: A change reason is present.
- `changes_requested` → Resubmit → `submitted`.
  - Actor: Request owner.
  - Preconditions: All required fields are valid.

Any state/action pair absent from this list is invalid and must not mutate state.

## Edit contract

- The request owner may edit request fields only in `draft` or `changes_requested`.
- Reviewers and administrators may not edit requester-supplied request fields.
- Assignment is cleared when a corrected request is resubmitted.
- A rejected or approved request cannot be edited in version 1.
- Concurrent edits use an explicit revision value; stale revisions fail without mutation.

## Transition input

The transition operations are:

- `submit_vendor_request`, accepting request identifier and expected revision.
- `assign_vendor_request`, additionally accepting the reviewer identifier.
- `review_vendor_request`, additionally accepting `approve`, `reject`, or `request_changes` and an
  optional decision reason.

A rejection or change request requires a trimmed reason from 1 through 1,000 characters. An approval
may include a reason under the same bounds. Actor identity, organization, and role are obtained from
authenticated database context.

## Transition output

A successful transition returns:

- Request identifier.
- Previous state.
- Current state.
- New revision.
- Committed audit event identifier.
- Transition timestamp generated by the database.

The request update and audit event are committed atomically. Neither may exist without the other.

## Audit contract

Creation and each successful state transition record an append-only event containing:

- Event identifier.
- Request identifier and organization identifier.
- Actor identifier and actor role at decision time.
- Action, previous state, and resulting state.
- Action reason when required.
- Database-generated timestamp.
- Resulting request revision.

The public application database role has no update or delete permission for audit events.
Sensitive credentials and authentication tokens must never appear in audit payloads.

## Stable error classes

Boundary failures use these stable application error codes:

| Code | Meaning | Mutation allowed |
| --- | --- | --- |
| `AUTHENTICATION_REQUIRED` | No valid authenticated identity exists. | No |
| `PERMISSION_DENIED` | The actor lacks role or resource permission. | No |
| `REQUEST_NOT_FOUND` | No visible request matches the identifier. | No |
| `VALIDATION_FAILED` | Input fields or action payload are invalid. | No |
| `INVALID_TRANSITION` | The action is not valid from the current state. | No |
| `STALE_REVISION` | The expected revision no longer matches. | No |
| `DEPENDENCY_UNAVAILABLE` | A required service is temporarily unavailable. | No partial mutation |
| `INTERNAL_ERROR` | An unexpected bounded failure occurred. | No partial mutation |

Database functions raise SQLSTATE `P0001` with the stable error code as the message. Public errors
expose that code and a safe user-facing message. They do not expose SQL, policies, stack traces,
credentials, or internal identifiers beyond the caller-visible resource.

To avoid disclosing cross-organization resource existence, an unauthorized read by identifier is
reported as `REQUEST_NOT_FOUND`. An authenticated mutation against an already visible request may
return `PERMISSION_DENIED`.

## Invariants

- Every request belongs to exactly one organization and one owner.
- Every assigned reviewer is an active reviewer in the request organization.
- Every request state is one of the six declared states.
- Every successful transition increments the revision exactly once.
- Every successful transition creates exactly one audit event in the same transaction.
- Failed validation, authorization, revision, and transition checks create no request mutation or
  audit event.
- Request and audit queries never return rows from another organization.

## Compatibility and evolution

Before the first public release, contract changes update this document and the corresponding tests
in the same change. After version 1 is public:

- Additive optional fields must preserve existing producer and consumer behavior.
- New states or actions require an explicit compatibility review of every existing transition.
- Renamed, removed, repurposed, or newly required fields require a migration or controlled cutover.
- Error code meanings must remain stable; replacement requires a documented deprecation period.
- Mixed schema/application versions must be tested before a database migration is deployed.

The contract currently has no deprecated fields or supported legacy versions.

## Required negative and boundary checks

Tests must verify:

- Every allowed transition succeeds only for its authorized actor.
- Every undeclared state/action pair fails without mutation.
- An owner cannot read or mutate another owner's private draft.
- A reviewer cannot act on an unassigned request.
- An administrator cannot use assignment authority to make a review decision.
- Cross-organization reads and mutations reveal no protected data.
- Required text and numeric fields reject values immediately outside each declared bound.
- Stale revisions fail without overwriting newer data.
- Audit events are unchanged after every failed operation.
